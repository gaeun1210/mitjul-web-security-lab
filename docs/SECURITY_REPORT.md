# 취약점 분석 및 조치 보고서 (SECURITY_REPORT)

밑줄(Mitjul) 랩의 취약점 6종을 아래 13항목 형식으로 정리합니다.
**코드 수정(저자 수행)**과 **실제 공격·방어 검증(VM에서 수행)**을 구분해 표기합니다.

> 검증 판정: PASS(실제 수행·기대 충족) / FAIL / PARTIAL / **NOT TESTED**(실행 환경 제약으로 미수행).
> 본 문서 작성 시점에 저자가 전체 스택을 직접 구동해 공격을 재현하지는 않았으므로, 공격 재현 결과는
> 대부분 **NOT TESTED**이며, 각 항목에 VMware Ubuntu에서 수행하는 절차를 함께 적었습니다.
> 실제 수행 결과는 `TEST_RESULTS.md`에 채웁니다.

코드 수준(테스트 하네스) 점검: 모든 PHP 파일 `php -l` 통과, 목(mock) DB로 전 페이지 렌더링 무오류,
XSS 출력 이스케이프·IDOR 403·CSRF 토큰 불일치 차단은 로직 단위로 확인함(실제 브라우저/도구 공격은 별도).

## 01. SQL Injection

1. **정의** — 사용자 입력이 SQL 질의문 구조에 개입해 인증 우회·비인가 데이터 조회/변조를 일으키는 취약점.
2. **발생 원인** — 입력값을 SQL 문자열에 직접 연결(문자열 결합).
3. **CWE / OWASP** — CWE-89 / OWASP A03:2021 Injection.
4. **관련 파일·기능** — 취약: `account/login_process.php`(로그인), `board/list.php`(검색), `board/view.php`(id), `register.php`, `account/edit.php`, `board/edit.php`·`delete.php`.
5. **취약 코드** — `"SELECT * FROM users WHERE username='$username' AND password='$password'"` 등 입력 직접 결합.
6. **보안 영향** — 로그인 우회, UNION으로 전체 회원·비밀번호 조회, `id=1 OR 1=1`로 대량 삭제/변조.
7. **실습 환경·재현 조건** — 취약 `http://localhost:8001`. 로그인 폼 아이디에 `admin' -- `(끝 공백), 검색창에 `zzz' UNION SELECT id, username, '-', password, '-', role FROM users -- `(목록이 6개 컬럼이라 6개로 맞춤).
8. **취약 버전 검증 결과** — **NOT TESTED**(VM에서 위 입력으로 재현). 기대: 비번 없이 admin 로그인, 검색 결과에 회원 비밀번호 노출.
9. **보완 코드·방어 원리** — 보완 전 파일에서 `prepare()`/`bind_param()`(Prepared Statement) 사용. 값이 SQL 구조와 분리돼 질의 구조를 못 바꿈. 숫자 파라미터는 `(int)` 캐스팅/`"i"` 바인딩.
10. **보완 버전 검증 결과** — **NOT TESTED**(VM, `http://localhost:8080`). 기대: `admin' -- ` 로그인 실패, UNION은 "결과 없음".
11. **HTTP 증빙** — VM에서 Burp/개발자도구로 요청·응답 캡처, 또는 sqlmap 로그(`REPRODUCE.md`).
12. **회귀 테스트** — 정상 로그인(`admin/Admin!234`)·검색 정상 동작 확인.
13. **한계·주의** — 비밀번호 저장 방식(05번)과는 별개 항목으로 구분. 내부 SQL 오류 메시지가 사용자에게 노출되지 않도록 보완 버전은 오류를 표출하지 않음.

## 02. XSS (Cross-Site Scripting)

1. **정의** — 저장/반사된 사용자 입력이 피해자 브라우저에서 스크립트로 실행되는 취약점.
2. **발생 원인** — DB/요청 값을 이스케이프 없이 HTML로 출력.
3. **CWE / OWASP** — CWE-79 / OWASP A03:2021 Injection.
4. **관련 파일·기능** — 취약: `board/view.php`(제목·내용·작성자명), `board/list.php`, `includes/header.php`(로그인 이름). 이 랩의 핵심은 **저장형(Stored)** XSS(게시글에 저장돼 열람자마다 실행).
5. **취약 코드** — `echo $post['title'];`, `echo nl2br($post['content']);` (이스케이프 없음).
6. **보안 영향** — 세션 쿠키 탈취(쿠키에 HttpOnly 미적용 시), 피싱/디페이스. 열람하는 모든 사용자(관리자 포함)가 피해.
7. **실습 환경·재현 조건** — 취약 8001, 로그인 후 문장 작성 "문장"칸에 `<script>alert('XSS')</script>` 저장 후 열람.
8. **취약 버전 검증 결과** — **NOT TESTED**(VM). 기대: 글 열람 시 alert 실행.
9. **보완 코드·방어 원리** — 출력 지점마다 `htmlspecialchars($v, ENT_QUOTES, 'UTF-8')`. 추가로 보완 버전은 세션 쿠키 `HttpOnly`(JS로 쿠키 접근 차단)와 기본 CSP를 적용.
10. **보완 버전 검증 결과** — **NOT TESTED**(VM, 8080). 기대: `<script>`가 글자 그대로 표시(실행 안 됨). (목 DB 로직 테스트에서는 이스케이프 출력 확인함.)
11. **HTTP 증빙** — 보완 응답 본문에 `&lt;script&gt;`로 인코딩되어 나오는지 캡처.
12. **회귀 테스트** — 한글·특수문자·줄바꿈이 정상 표시되는지 확인.
13. **한계·주의** — **반사형(Reflected)** XSS는 이 랩에 별도 입력 지점을 두지 않았음(검색어 출력은 보완 버전에서 이스케이프 처리). "스크립트 실행 차단(이스케이프)"과 "쿠키 접근 차단(HttpOnly)"은 별개 방어이므로 구분해 설명.

## 03. IDOR / 권한 우회 (Broken Access Control)

1. **정의** — 로그인 여부만 확인하고 "대상의 소유자/권한"을 서버에서 재검증하지 않아, 남의 리소스에 접근/변조하는 취약점.
2. **발생 원인** — 화면에서만 버튼을 숨기고, 처리 코드에서 소유자/관리자 검사를 누락.
3. **CWE / OWASP** — CWE-639 / OWASP A01:2021 Broken Access Control.
4. **관련 파일·기능** — 취약: `account/edit.php`·`delete_account.php`(URL id 신뢰), `board/edit.php`·`delete.php`(작성자 미검증).
5. **취약 코드** — `$id = $_GET['id'] ?? $_SESSION['user_id'];` 후 소유자 확인 없이 처리.
6. **보안 영향** — 다른 회원 정보/비밀번호 변경·탈퇴, 타인 게시글 수정·삭제.
7. **실습 환경·재현 조건** — 취약 8001, 일반 계정 `yuna` 로그인 후 `board/edit.php?id=2`(타인 글) 접근.
8. **취약 버전 검증 결과** — **NOT TESTED**(VM). 기대: 타인 글 수정폼이 열림/수정됨.
9. **보완 코드·방어 원리** — 처리 직전 서버에서 `canManagePost()`로 소유자/관리자 재검증, 회원정보 수정/탈퇴는 URL id 무시하고 **세션 본인 id만** 사용. 관리자 경로는 `requireAdmin()`.
10. **보완 버전 검증 결과** — **NOT TESTED**(VM, 8080). 기대: 타인 글 `board/edit.php?id=2` → 403. 회원정보 수정은 본인 것만 열림(타인 정보 노출/변경 불가). (목 DB 로직 테스트에서 403 확인함.)
11. **HTTP 증빙** — 403 응답 캡처.
12. **회귀 테스트** — 작성자/관리자는 자기 글·관리 기능 정상 수행.
13. **한계·주의** — **공개 게시글 조회는 정상 기능이며 IDOR이 아님.** 보완 회원정보 수정은 403이 아니라 "URL id 무시+본인 id 사용"으로 막으므로, 판정은 **타인 정보가 실제로 노출/변경되는지**를 기준으로 함. CSRF(04번)와 혼동하지 말 것.

## 04. CSRF (Cross-Site Request Forgery)

1. **정의** — 로그인된 피해자의 브라우저가 공격자 의도대로 상태변경 요청을 대신 보내게 되는 취약점.
2. **발생 원인** — 요청이 "해당 사이트의 폼에서 생성됐는지" 증명하는 토큰 부재.
3. **CWE / OWASP** — CWE-352 / OWASP A01:2021 Broken Access Control.
4. **관련 파일·기능** — 상태변경 폼 전반(문장 작성·수정·삭제, 회원정보 수정·탈퇴).
5. **취약 코드** — 취약 버전엔 CSRF 토큰 자체가 없음.
6. **보안 영향** — 피해자가 링크만 열어도(IDOR 결합 시) 글 삭제·계정 변경 등이 실행.
7. **실습 환경·재현 조건** — 취약 8001 로그인 상태에서 외부 HTML 폼으로 `board/delete.php`에 POST.
8. **취약 버전 검증 결과** — **NOT TESTED**(VM). 기대: 토큰 없이 삭제 성공.
9. **보완 코드·방어 원리** — 세션에 `random_bytes(32)` 토큰 1회 발급, 상태변경 폼에 hidden으로 심고 처리 직전 `hash_equals()`로 검증. 로그인 성공 시 토큰 재발급, SameSite=Lax 유지.
10. **보완 버전 검증 결과** — **NOT TESTED**(VM, 8080). 기대: 토큰 없는/틀린 요청은 403. (목 DB 로직 테스트에서 토큰 불일치 403 확인함.)
11. **HTTP 증빙** — 토큰 누락 요청의 403 응답 캡처.
12. **회귀 테스트** — 정상 폼 제출은 정상 동작.
13. **한계·주의** — CSRF와 IDOR는 각각 독립 검증. 토큰 검증 실패 시 내부 오류를 노출하지 않음(고정 메시지). **로그인 폼 CSRF 토큰·로그아웃 GET→POST 전환은 추가 개선 항목으로 보류**(CHANGELOG 참고).

## 05. 비밀번호 평문 저장

1. **정의** — 비밀번호를 복원 가능한 형태(평문)로 저장해, 유출 시 즉시 악용되는 취약점.
2. **발생 원인** — 저장 시 단방향 해시를 적용하지 않음.
3. **CWE / OWASP** — CWE-256 / OWASP A02:2021 Cryptographic Failures.
4. **관련 파일·기능** — 취약: `register.php`(저장), `login_process.php`(비교), `account/edit.php`, `reset_password.php`.
5. **취약 코드** — `INSERT ... VALUES ('$username','$password',...)` / `WHERE password='$password'`(평문 비교).
6. **보안 영향** — SQLi(01) 유출 시 해시 크랙 없이 즉시 로그인, 타 사이트 크리덴셜 스터핑.
7. **실습 환경·재현 조건** — 취약 8001, 01번 UNION/`sqlmap --dump`으로 `users` 조회 시 평문 비밀번호가 그대로 보임.
8. **취약 버전 검증 결과** — **NOT TESTED**(VM). 기대: DB/덤프에 평문 비밀번호.
9. **보완 코드·방어 원리** — 저장 `password_hash($pw, PASSWORD_DEFAULT)`(bcrypt), 검증 `password_verify()`. 가입·재설정 모든 저장 경로에 적용. 시드 계정도 해시로 적재.
10. **보완 버전 검증 결과** — **NOT TESTED**(VM). 기대: `SELECT password FROM mitjul_secure.users` 가 `$2y$...` 해시.
11. **HTTP 증빙** — 해당 없음(DB 조회 결과로 증빙).
12. **회귀 테스트** — 정상 로그인·비밀번호 변경 후에도 해시로 저장·검증.
13. **한계·주의** — "해시(단방향)"를 "암호화"로 표현하지 말 것. SQLi 차단 결과(01)와 비밀번호 저장 방식(05)은 **별도 항목으로 구분**해 검증.

## 06. 파일 업로드 및 RCE

1. **정의** — 업로드 파일의 종류/저장/실행을 통제하지 않아, 서버에서 실행되는 코드(웹쉘) 업로드로 원격 코드 실행이 가능한 취약점.
2. **발생 원인** — 확장자·MIME 미검증 + 웹에서 접근 가능한 경로에 예측 가능한 이름으로 저장 + 스크립트 실행 미차단.
3. **CWE / OWASP** — CWE-434 / OWASP A05:2021 Security Misconfiguration.
4. **관련 파일·기능** — 취약: `board/write.php`(과제/이미지 첨부 저장).
5. **취약 코드** — `$stored = $post_id."_".$original; move_uploaded_file(...);` (검증 없음, 원본 이름 사용).
6. **보안 영향** — `shell.php` 업로드 후 `uploads/N_shell.php?cmd=...` 접근으로 서버 명령 실행(웹서버 프로세스 권한).
7. **실습 환경·재현 조건** — 취약 8001, `<?php system($_GET['cmd']); ?>`를 `shell.php`로 첨부 업로드 후 접근.
8. **취약 버전 검증 결과** — **NOT TESTED**(VM, 격리 환경에서 무해한 테스트 명령으로). 기대: `?cmd=id` 결과 표시.
9. **보완 코드·방어 원리** — 보완 `board/write.php`: 확장자 화이트리스트(jpg/png/gif/webp) + `finfo` MIME 검사(불일치 거부) + `random_bytes` 랜덤 파일명. 추가로 `app/secure/uploads/.htaccess`에서 `.php` 류 실행을 `Require all denied`로 차단.
10. **보완 버전 검증 결과** — **NOT TESTED**(VM, 8080). 기대: 비이미지 거부, 저장돼도 실행 시 403.
11. **HTTP 증빙** — 업로드 거부 메시지, 업로드 경로 접근 시 403 응답 캡처.
12. **회귀 테스트** — 정상 이미지(jpg/png) 업로드·조회 정상.
13. **한계·주의** — **"파일 업로드 거부"와 "서버 측 실행 차단"은 별개**이므로 구분 검증(둘 다 필요). 반드시 **격리된 로컬 환경에서 무해한 테스트 파일**로만 수행. 업로드 파일 웹루트 외부 저장·이미지 재인코딩은 추가 개선 항목으로 보류.
